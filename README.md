# coder-agent

Автономный кодер-агент на локальных моделях через Ollama (qwen2.5-coder:7b — план,
qwen3.5:9b — код, qwen3:8b — тестер/аудитор). Роли переключаются автоматически;
модели ротационно загружаются/выгружаются (keep_alive=0), что позволяет работать
на RTX 4060 8GB + 16GB RAM с контекстом 16384.

## Запуск

```powershell
python -m coding_agent "Напиши чат-приложение с аутентификацией, личные и групповые чаты."
```

Все файлы проекта пишутся в папку `workflow/<имя-проекта>/` (код + состояние `agent_state/`).
В текущей директории ничего не создаётся.

- Имя проекта генерируется из запроса автоматически (транслитерация в slug), либо задаётся явно:
  `python -m coding_agent "..." --name my-chat`
- Повторный запуск с тем же запросом продолжает существующий проект (resume с сохранённого состояния).
- Новый проект с таким же именем создаётся с суффиксом `-2`, `-3` и т.д.
- `--fresh` — очистить состояние плана/задач выбранного проекта и начать заново.
- Каталог workflow можно задать переменной окружения `CODER_AGENT_WORKFLOW`.

## Прогресс-бар

Во время работы в консоли внизу обновляется одна строка прогресса:

```
[ 33%] ████████████░░░░░░░░░░░░░░░░░░░░░░░░ 2/6 | Аутентификация      | КОД            | ⏱ 4м12с ETA 8м30с
```

- процент и заполнение — по **обработанным** задачам (принятые + проваленные);
- фаза справа: `ПЛАН` → `КОД` / `ОТЛАДКА(n/3)` → `РЕ-ПЛАН` → `СВЕРКА`;
- `⏱` — время текущей сессии, `ETA` — оценка остатка по средней скорости задач;
- состояние бара сохраняется в `agent_state/bar.json` и восстанавливается при resume;
- бар печатается только в интерактивной консоли (TTY). В перенаправленный файл/pipe
  идут только обычные логи. Отключить полностью: `CODER_AGENT_NO_BAR=1`.

## Структура

```
workflow/
└── napishi-chat-prilozhenie-s-autentifikats/   # id проекта (slug)
    ├── app.py, main.py, tests/...              # код проекта
    └── agent_state/                            # состояние агента
        ├── request.txt                         # запрос (по нему идёт resume-поиск)
        ├── plan.md, tasks.json, progress.md
        ├── bar.json                            # снапшот прогресс-бара (resume)
        ├── audit_report.md                     # финальная сверка с планом
        └── run.log
```

Каждый проект — отдельный git-репозиторий (коммит на каждую принятую задачу).
Реальные проверки (py_compile, smoke-import, unittest/pytest) выполняются внутри
каталога проекта.

## Безопасность smoke-проверок

Модели часто пишут чат-приложения с запуском веб-сервера прямо в модуле
(`socket.bind`, `uvicorn.run`, `flask.run`). При smoke-импорте это заблокировало бы
проверку до таймаута и заняло порт, поэтому оркестратор AST-сканирует каждый файл:
файлы с «серверными» и опасными вызовами (`eval/exec/os.system/subprocess/...`)
не исполняются — они только компилируются, а тестер получает предупреждение `[WARN]`.
Запуск сервера остаётся на совести пользователя: приложение запускается вручную
(например, `uvicorn main:app`), код под `if __name__ == "__main__":` при этом не блокируется.

Сетевые сбои Ollama обрабатываются автоматически: HTTP 5xx (временная нехватка VRAM,
рестарт сервиса) ретраится на той же модели с паузой, ошибки соединения повторяются один раз,
при стабильном отказе primary включается fallback-модель; бесконечных циклов нет.
